# v0.6.16 — `_safe_int_mb` accepts V4 decimal + V4 NetworkInterface nested schema

User supplied real-device XML responses from their Hikvision fleet
(2026-09-25 08:44 — NVR.txt + IPC.txt). Three previously-undetected
parsing bugs came to light:

## Bug 1 — V4 NVR memoryUsage is a decimal, not an integer

The user's V4 NVR (`DS-7708N-I4` V4.1.18 firmware) returned:

```xml
<MemoryList>
  <Memory>
    <memoryDescription>DDR Memory</memoryDescription>
    <memoryUsage> 728.234375</memoryUsage>
    <memoryAvailable> 402.613281</memoryAvailable>
  </Memory>
</MemoryList>
```

V4 firmware reports memory as **decimal MB** (with optional leading
whitespace); V5 reports as **integer MB** (`<memoryUsage>61</memoryUsage>`).

Pre-v0.6.16 `_safe_int_mb` was:

```python
return int(str(value).strip())   # int("728.234375") → ValueError
```

→ returned `None` → all four memory sensors (`memory_usage`,
`memory_available`, etc.) silently showed "Unknown" on every V4
NVR despite the device returning perfectly valid data.

**Fix**: `_safe_int_mb` now parses as float and rounds:
`int(round(float(str(value).strip())))`. Both V5 integers and V4
decimals return their integer MB value.

## Bug 2 — V4 NVR `<NetworkInterface>` nests the IP fields

V4 NVR firmware wraps IP/subnet/gateway inside another
`<IPAddress>` container:

```xml
<NetworkInterface>
  <id>1</id>
  <IPAddress>
    <ipVersion>dual</ipVersion>
    <ipAddress>10.18.176.65</ipAddress>
    <subnetMask>255.255.255.0</subnetMask>
    <DefaultGateway><ipAddress>10.18.176.1</ipAddress></DefaultGateway>
  </IPAddress>
  <Link><MACAddress>...</MACAddress></Link>
</NetworkInterface>
```

V5 schema (where this worked):

```xml
<NetworkInterface>
  <id>1</id>
  <IPAddress>192.168.1.10</IPAddress>
  <subnetMask>255.255.255.0</subnetMask>
  <DefaultGateway>192.168.1.1</DefaultGateway>
</NetworkInterface>
```

Pre-v0.6.16 `_parse_network_interfaces` only handled V5:
`_xml_text(iface, "IPAddress")` returned the text content of
`<IPAddress>`, which for V4 was an empty string (because the
V4 `<IPAddress>` element is a *container*, not a leaf).

**Fix**: `_parse_network_interfaces` now has an `_ip_field`
helper that tries V4 nested paths first then falls back to V5
direct text. Each field's V4 path is documented inline. Network
sensors (`ip_address`, `subnet_mask`, `default_gateway`) now
populate on V4 NVRs.

## Bug 3 — V4 status parser fed raw whitespace-padded string to sensor

`_parse_system_status` was passing the raw text of `<memoryUsage>`
(including the V4 leading whitespace) into the dict. Even after
fix #1 above, the dict-level parser wasn't converting to int —
`_parse_system_status` now wraps the field with `str(_safe_int_mb(...) or 0)`
so the dict consistently holds integer strings.

## Tests added (11 new in test_v0616_real_fixtures.py)

All tests use the user's actual XML responses as fixtures:

- `test_safe_int_mb_accepts_decimal_string` — `"728.234375"` → 728.
- `test_safe_int_mb_accepts_decimal_with_whitespace` — `" 728.234375"` → 728.
- `test_safe_int_mb_accepts_float_that_rounds_up` — banker's rounding.
- `test_parse_system_status_v4_dvr_decimal_memory` — exact real
  V4 NVR `<DeviceStatus>` from the user's fleet.
- `test_parse_system_status_v5_ipc_integer_memory` — exact real
  V5 IPC `<DeviceStatus>` to confirm V5 still works.
- `test_parse_device_info_v4_dvr` — exact real V4 `<DeviceInfo>`.
- `test_input_proxy_channels_with_wrong_size_attribute` — the
  user's NVR returns `<InputProxyChannelList size="0">` but
  contains 8 actual channels. Our `findall(".//InputProxyChannel")`
  counts children correctly (the size attribute is ignored).
- `test_parse_network_interfaces_real_dual_nic_dvr` — exact real
  dual-NIC V4 NVR with 10.18.176.65 + 192.168.10.10 on same MAC prefix.
- `test_v0616_manifest_version_bumped`.

Plus `_fetch_storage` now tries three endpoint candidates before
declaring "missing":
1. `/ISAPI/ContentMgmt/storage`
2. `/ISAPI/System/Storage/hardDisks`
3. `/ISAPI/ContentMgmt/storage/hddList`

On the user's V4 NVR all three return `<ResponseStatus>` 4
"Invalid Operation" — the firmware refuses the storage family
entirely. The new code surfaces this fact in the INFO log and
skips silently for IPCs (which legitimately have no storage).
The summary log `storage=missing` line still tells the user which
storage state they have.

## What still won't work on the user's V4 NVR

The user's `DS-7708N-I4` V4.1.18 firmware returns
`<ResponseStatus>` 4 "Invalid Operation" for ALL THREE storage
endpoints tested. There's no public ISAPI path on this firmware
that exposes HDDs — V4 NVRs in this state cannot be queried for
storage over ISAPI. The four storage sensors will remain "未知"
on this specific device. There's no integration-side fix
without firmware access.

`refresh summary:` for the V4 NVR will look like:

```
INFO 192.168.10.10 refresh summary: device_info=OK channels=8
     storage=missing network=OK status=OK bitrate=missing
```

(i.e. only `storage` and `bitrate` stay missing; everything else
now populates.)
