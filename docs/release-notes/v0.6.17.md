# v0.6.17 — sensor cleanup: CPU/MAC fixed, storage removed, uptime hours-only, 7 new device-info sensors

User feedback (2026-09-25 09:30+): after v0.6.16 the integration
showed entity-level data, but:

- **CPU 使用率 doesn't show** — sensor key mismatch in
  `value_fn`.
- **MAC 地址 doesn't show** — V4 NVR firmware nests MAC inside
  `<Link>`, the parser only looked at direct children.
- **4 storage sensors don't show** — the user's V4 NVR refuses
  the entire storage family with `<ResponseStatus> 4 Invalid
  Operation` for every endpoint variant, so these will always
  be "unknown" on this device.
- **内存使用率 shows 358%** — the sensor was passing through
  raw MB (V4 returns `728.234375` MB) under a `PERCENTAGE` unit.
  HA rendered it as "728%" (and on a different test device it
  might've shown "358%" depending on how the % was miscomputed).
- **运行时长** — user wants hours, not seconds.
- **能显示没做上的传感器加上** — several sensors where we already
  have the data but never exposed it as an entity.

All addressed below.

## Bug fixes

### 1. `cpu_usage` key mismatch (silent bug, present since v0.1.0)

Sensor's `value_fn` was `d.system_status.get("cpuUsage")`. The
coordinator parses with key **`cpuUtilization`** (matches Hikvision's
XML element). Pre-v0.6.17 the look-up always returned `None` and
the sensor always showed "unknown" — even though CPU is one of
the most common ISAPI metrics.

**Fix**: `value_fn` now reads `cpuUtilization`.

### 2. `memory_usage` showed raw MB as percent

`<memoryUsage>` from `/ISAPI/System/status` is the **absolute MB
used** (V4 reports it as decimal MB with whitespace prefix). The
sensor had `native_unit_of_measurement=PERCENTAGE` and read the
raw value, so HA displayed "728%" on the user's V4 NVR.

**Fix**: New `_memory_usage_percent(data)` helper computes
`used / (used + available) * 100` rounded to 1 decimal. The
sensor's translation key is `memory_usage` (preserved for
existing HA entity_ids / dashboards) and the actual displayed
unit is now correct. A companion `memory_available_mb` sensor
exposes the raw available MB value (useful for monitoring
constrained-RAM IPCs).

### 3. `network_mac` empty on V4 NVR

V4 NVR firmware wraps the MAC address inside `<Link>`:

```xml
<NetworkInterface>
  <IPAddress>...</IPAddress>
  <Link>
    <MACAddress>02:00:00:00:00:0e</MACAddress>
    ...
  </Link>
</NetworkInterface>
```

Pre-v0.6.17 `_parse_network_interfaces` only read
`MACAddress` as a direct child, missing the V4 nested path. V5
firmware has `MACAddress` as a direct child so it worked there.

**Fix**: New `_mac_address(iface)` helper tries `Link/MACAddress`
(V4) first, falls back to direct `MACAddress` (V5). Both
firmware generations now populate the `network_mac` sensor.

## Sensors deleted (per user request)

- `storage_total` (存储总量)
- `storage_used` (存储使用量)
- `storage_free` (存储剩余)
- `storage_usage` (存储使用率)

The 4 storage sensors are removed from the `SENSORS` tuple.
On the user's V4 NVR (`DS-7708N-I4` V4.1.18), every storage
endpoint variant (`/ContentMgmt/storage`,
`/System/Storage/hardDisks`, `/ContentMgmt/storage/hddList`)
returns `<ResponseStatus> 4 Invalid Operation`. These sensors
would have been "unknown" forever on this device; the user
asked to remove them rather than see perpetual "unknown".

For other V4/V5 NVR firmwares that DO serve storage, this is a
regression. v0.6.18+ can re-introduce per-device storage
support as a separate option if the user reports a use case.

- `uptime` (运行时长, seconds) — duplicate of `device_uptime`.
- `device_uptime` (运行时长, seconds) — replaced by `uptime_hours`.

Both seconds-based sensors are deleted; only the new
`uptime_hours` (单位 HOURS, 1 decimal) remains.

- `channel_1_uptime`, `channel_1_reboot_count`,
  `sd_card_writes`, `dome_high_temp_runtime` — the per-channel
  status endpoint returns `<ResponseStatus> 4` for the user's
  V4 NVR. They were "unknown" on the user's fleet and the user
  asked to remove sensors the integration "doesn't have" (i.e.
  the device doesn't expose the data).

## Sensors added (data already parsed, never exposed)

- `device_mac` — from `deviceInfo.macAddress` (canonical hardware
  MAC, distinct from per-NIC MAC).
- `device_type` — IPC / NVR / DVR / IPZoom (text from
  deviceInfo). Useful for fleet dashboards.
- `device_id` — UUID from `<deviceID>`. Distinguishes
  physically-identical units.
- `firmware_release_date` — `build 240522`-style date string from
  `<firmwareReleasedDate>`.
- `encoder_version` — V4 firmware's `<encoderVersion>` (often
  empty on V5).
- `encoder_release_date` — V4 firmware's `<encoderReleasedDate>`.
- `memory_available_mb` — raw MB available (unit MB,
  `DATA_SIZE` device class). For monitoring low-RAM IPCs.

The set of available data wasn't increased — all of these were
already in the parsed `_parse_device_info` / `_parse_system_status`
dicts but not surfaced. v0.6.17 just exposes them.

## Compatibility

- `manifest.json.version` bumped 0.6.16 → 0.6.17.
- Sensor entity IDs for the kept sensors (`型号`, `序列号`,
  `CPU 使用率`, `运行时长`, etc.) are unchanged — translation
  keys are preserved.
- Users who registered the deleted storage / per-channel /
  seconds-uptime sensors in their HA dashboard will see them
  disappear on the next HA reload. Re-add via manual entity
  definition if you need historical tracking.
- The `cpu_usage` and `memory_usage` translation keys are
  preserved (HA entity_id won't change) even though the
  displayed unit / computation changed. This keeps dashboards
  stable while fixing the values.
