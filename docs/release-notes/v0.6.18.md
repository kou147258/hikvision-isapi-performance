# v0.6.18 — re-add storage + add video encoding / streaming detail sensors

User feedback (2026-09-25 09:38+): after v0.6.17's cleanup the
entity list dropped 4 storage sensors and the streaming-detail
fields they'd never populated on the user's V4 NVR. The user
pointed out that **storage / encoding / bitrate** information is
valuable and should be re-exposed — even if it stays "unknown"
on firmware versions that don't serve the endpoints.

This release reverses that part of v0.6.17 (storage sensors back)
and adds a new family of streaming-detail sensors extracted from
the `<StreamingChannel>` XML on V5 IPCs.

## Restored (after v0.6.17's over-eager cleanup)

The 4 storage sensors, now with explicit GB units (HA's preferred
HDD unit):

| Sensor | Translation key | Native unit |
|--------|------------------|--------------|
| 存储总量 (GB) | `storage_total` | GIGABYTES |
| 存储已用 (GB) | `storage_used` | GIGABYTES |
| 存储剩余 (GB) | `storage_free` | GIGABYTES |
| 存储使用率 | `storage_usage` | PERCENTAGE |

On the user's V4 NVR (`DS-7708N-I4` V4.1.18), these still show
"unknown" — the firmware returns `<ResponseStatus> 4 Invalid
Operation` for the entire storage family. v0.6.16's
3-endpoint-fallback (`/ContentMgmt/storage` →
`/System/Storage/hardDisks` → `/ContentMgmt/storage/hddList`) keeps
running; if any future firmware serves one of those, the sensors
populate automatically.

## New streaming-detail sensors

The user's V5 IPC `<StreamingChannel>` XML (from `IPC.txt`) had
rich video/audio fields we'd parsed but never surfaced. v0.6.18
exposes them:

| Sensor | Unit | Example value |
|--------|------|---------------|
| 通道 1 视频编码 | (text) | `H.264` |
| 通道 1 分辨率 | (text) | `1920x1080` |
| 通道 1 帧率 | fps | `16.0` (Hikvision reports `maxFrameRate` in hundredths: `1600` → `16 fps`) |
| 通道 1 码率 | kbps | `2048` |
| 通道 1 音频编码 | (text) | `G.711alaw` |

These populate on V5 IPCs (verified against the user's
`DS-FB2127` IPC.txt response). On the user's V4 NVR (which
returns `<ResponseStatus> 4` on `/Streaming/channels`) they stay
"unknown" — and the coordinator's per-endpoint fault-tolerance
won't crash the refresh.

`_parse_streaming_detail` correctly handles Hikvision's nested
`<Video>` / `<Audio>` element grouping (the codec fields live
inside `<Video>`, audio fields inside `<Audio>`) by doing
descendant-context lookups rather than direct-child reads. H.264 /
H.265 / MJPEG codecs all work; resolution / frame rate / audio
are populated as None when the corresponding XML is absent.

## Coordinator plumbing

A new `HikvisionISAPIData.streaming_channel_detail` field holds
the parsed streaming detail. The coordinator fetches
`/Streaming/channels` (V5 IPC) already; v0.6.18 just makes the
parsed shape richer.

  size storage sensors use `UnitOfInformation.GIGABYTES`.

## Compatibility

- `manifest.json.version` bumped 0.6.17 → 0.6.18.
- No public-API changes.
- Translation keys for restored storage sensors match v0.6.16,
  so users who had `storage_total` etc. registered in HA
  dashboards will see them repopulate (different entity name
  internally — `storage_total_gb` instead of `storage_total` —
  but HA matches by translation_key).
- Translation keys for new streaming sensors are new
  (`channel_1_video_codec` etc.). They'll register fresh on
  first HA reload.
